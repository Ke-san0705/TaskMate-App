# TaskMate Mobile: Museからのタスク受信

作成日: 2026-11-10（日本時間）
状態: 実装前の設計確認用

## 目的と合意済みの方針

Museが取得したタスクを、手で転記せずTaskMateスマホ版へ追加できるようにする。
利用者は「追加専用API＋Supabaseの受信箱」を選択済み。
アプリを閉じている間の即時反映や通知は不要で、次回起動時に反映すればよい。
起動時に加え、バックグラウンドから復帰した際と手動操作でも取得する。

## 現状と制約

- Android先行のExpo / React Nativeアプリ。通常タスクは端末内SQLiteへ保存している。
- 現行スマホ版にはSupabaseクライアント、ログイン、タスク取り込みAPIはない。
- PC版にはSupabase認証・同期コードとSQLがあるが、スマホ版へそのまま移植できる状態ではない。
- 通常タスクは日付必須。時刻は任意。タイトル・説明などの検証処理を共有コアが持つ。
- 通常の追加後には画面・通知・集中状態・ウィジェットを更新する既存処理がある。
- 作業フォルダには利用者の未コミット変更が多数ある。既存変更を保全して実装する。
- 本設計の承認は有料プラン購入や公開環境へのデプロイの承認を兼ねない。

## 検討した方法

1. JSONの貼り付け・共有取り込み。クラウド不要だが、利用者の転記操作が残る。
2. 追加専用APIとSupabaseの受信箱。認証・サーバー運用は必要だが、自動で受け渡しできる。

利用者は2を選択した。公式コネクタ一覧への掲載申請やMCPサーバーは初版に含めず、
MuseのCustom Connectorから呼べるHTTP APIと利用手順を用意する。

## 初版の範囲

- 通常タスクの追加のみ。編集・削除・完了操作・プロジェクト取り込み・PC同期は含めない。
- Museが追加したタスクだけをクラウドへ保存する。既存の端末内タスクはアップロードしない。
- 接続していない場合も、既存のローカル機能を使える。
- 即時プッシュ、常時接続、バックグラウンドの定期通信は行わない。
- 初版は1アカウントにつき受信先のスマホ1台を想定する。複数端末間の再配布・同期は行わない。
- 初版のログインはSupabaseに作成済みのアカウントのメール／パスワード認証とする。
  アプリ内の新規アカウント作成は追加せず、検証用アカウントの作成方法を導入手順に記載する。
  これは実装側の初版提案であり、利用者からの指定事項ではない。

## 構成

MuseはHTTPSの追加APIにタスクを送信する。Edge Functionは連携キーを検証し、
対応する利用者の受信箱へ保存する。スマホ版はSupabase Authで本人確認したうえで
未取り込みの項目を取得し、SQLiteへ登録してからサーバーへ取り込み済みを通知する。

SupabaseのDBとEdge Functionsを使用し、別の常駐Webサーバーは用意しない。
既存のtask_sync_itemsはPC同期の責務を持つため、この受信箱には使用しない。

## 認証とキー管理

- スマホには公開可能なSupabase URLとpublishable keyのみを設定する。
- スマホのセッションは永続化し、復帰時に期限切れトークンを更新する。
  Supabaseクライアントの標準認証処理を利用する。保存方式の詳細は実装で選ぶ。
- 利用者が設定画面から、Muse用の追加専用キーを発行・失効できる。
- キーは暗号学的乱数で生成する。サーバーにはハッシュのみ保存し、平文は発行直後だけ表示する。
- キーはHTTPヘッダーで送信する。通常の会話、URL、ログには含めず、Museの資格情報保存機能で設定する。
- キーには他のタスクの取得・変更・削除権限を与えない。発行者の利用者IDにサーバー側で固定する。
- 本人向けの管理・取得・受領確認操作は、有効なSupabase Authセッションを必須とする。
- 全受信箱テーブルをRLSで利用者ごとに分離する。service-role/secret keyはEdge Function内だけで使用する。
- 通常のログアウトはスマホの取得を停止する。Museからの追加を止める操作はキーの失効として別に明示する。
- ログインは受信箱の接続先を選ぶ操作であり、端末内タスクをアカウント別に切り替える機能ではない。
  Aで取り込んだタスクは、ログアウト後やBへのログイン後も同じ端末に残る。設定画面にこの挙動を明記する。

## 追加APIの契約

- 1リクエストにつき最大50件、ボディ上限64KBとする。
- 各項目は連携元で安定したexternalId、title、dateを必須とする。
- 任意項目はdescription、time、genre、priority。completedや端末内IDは送信者に指定させない。
- dateは実在するYYYY-MM-DD、timeはHH:mmまたは空とする。
- 初版の日時は日本時間（Asia/Tokyo）として定義し、その前提を接続手順に明記する。
  端末のタイムゾーンが日本以外の場合は、自動取り込みを保留して理由を表示する。
- 日付不明のタスクはAPIで受け付けず、どの項目に日付が必要かを返す。Museに推測で日付を補わせない。
- 文字数・優先度などは共有コアと同じ制限にする。
- バッチ全体を検証した後、トランザクションで登録する。入力不備は全体を拒否し、項目ごとの理由を返す。
- (user_id, source, external_id)を一意にし、同じ項目の再送では新規追加や上書きをしない。
  同じexternalIdで内容が異なる場合は競合として返す。
- sourceは初版ではmuse固定。同じ利用者がキーを再発行しても重複判定を維持する。
- 成功結果は「受信箱へ保存済み」を表し、「スマホへ追加済み」とは区別する。
- 認証失敗、形式不備、内容競合、上限超過、通信障害を区別する応答を用意する。
- DB側で原子的に利用上限を適用する。初版はキーごとに1日200件、利用者ごとに有効キー最大3本を既定値とする。
  これらの数値は実装側の提案であり、必要になれば変更可能とする。

## サーバーと端末のデータ

サーバー:

- 連携キー: 利用者ID、ハッシュ、表示用末尾、発行日時、失効日時、使用日時、上限管理情報。
- 受信箱: UUID、利用者ID、source、externalId、正規化した入力のハッシュ、検証済みタスク情報、受信日時、取り込み済み日時。
- タスク情報は取り込み済み通知後に削除し、再送防止と内容競合の判定に必要なexternalId・入力のハッシュ・状態を保持する。
- 未取り込みのタスクと再送防止記録に自動期限は設けず、本人による連携データ削除またはアカウント削除まで保持する。
  初版は期限切れによる取りこぼしを避ける方針とし、ストレージ使用量の確認手順を導入文書に記載する。
- 取り込み済みの本文は再配布できない。再インストール後の復元や2台目への配布は初版の対象外とし、説明に明記する。
- 利用者のAuthアカウント削除時には関連行も削除する。

端末:

- SQLiteに取り込み記録テーブルを追加する。利用者IDと受信箱UUIDで一意にする。
- Muse由来の識別情報を保持し、既存のmanual/projectの扱いを壊さない。
- サーバー受信箱UUIDと利用者IDから安定した端末内タスクIDを決めるか、取り込み記録に対応するIDを保存する。
- 通常タスクと取り込み記録は同じSQLiteトランザクションで保存する。
- ローカルタスクを後から編集・削除しても、受領確認の再試行によって再作成・上書きしない。
- ローカルデータの全削除は取り込み記録とログイン状態も消す。サーバーの未取り込み分とキーは残る旨を画面に明記する。

## 取得処理と障害時の動作

1. アプリのローカル初期化後、接続設定とセッションが有効なら未取り込み分を取得する。
2. 復帰時・手動取得時にも同じ処理を実行する。同時取得は1本へまとめる。
3. 一度に最大50件を受信し、継続分をページ単位で処理する。
4. 各項目を端末側でも検証する。サーバーのデータも無条件には信用しない。
5. トランザクションでタスクと取り込み記録を保存する。
6. 既存の更新経路で画面、締切通知、ウィジェットへ反映する。集中モードを自動開始しない。
7. 保存済みの項目に限り取り込み済みを通知する。受領確認に失敗した場合は後で再送する。

オフラインやサーバー障害でローカル起動を失敗させない。有限の通信タイムアウトを設ける。
受領確認前にアプリが終了しても次回に重複せず回復する。
認証エラーは再ログインを案内し、無限の自動再試行はしない。
ログアウトや別アカウントへの切り替えが処理中に起きた場合、取得開始時の利用者を確認して
切り替え後の状態へ古い結果を反映しない。
無効な項目を検出した場合は、その項目を取り込み済みにはせず、他の正常な項目は処理できるようにする。

## スマホの設定画面

「外部タスク連携」を追加し、次を表示する。

- 連携の説明と、Muse由来のタスクがSupabase経由で届くこと。
- 未設定時の案内、ログイン欄、ログイン中のアカウント、ログアウト。
- 自動取得の有効／無効、手動取得、最終取得日時・追加件数・エラー。
- Muse用キーの発行、発行直後の安全な引き渡し案内、既存キーの失効。
- 連携停止とログアウトの違い。
- サーバー上の連携データを削除する操作。本人認証と確認後、受信箱とキーを削除する。
  この操作は端末へ取り込み済みの通常タスクを削除しない。再接続後は再送防止記録もなくなる旨を説明する。

未接続ユーザーにもログインを強制しない。既存の「アカウントなし」「外部送信なし」という説明は、
通常機能と任意の外部連携の実態に合う表現へ更新する。
プライバシー文書にも、受信箱に保存する情報、用途、削除方法を追記する。

## 検証と完了条件

- 正常な1件・複数件の受信とSQLite登録。
- 無効キー、失効キー、他利用者による取得・受領確認の拒否。
- API再送、並行送信、端末保存後の受領確認失敗、再起動、手動削除後の再取得で重複しない。
- 入力不備、期限未定、違うタイムゾーン、サイズ・件数上限、レート制限。
- オフライン・タイムアウト・ログアウト・利用者切り替えで既存タスクを失わない。
- 共有コア、スマホ、デスクトップの既存テストとAndroid向けバンドルを確認する。
- SQL/RLSとEdge FunctionはローカルSupabase環境が利用できれば結合検証する。
  利用できなければ、その検証が未実施であることを明記し、デプロイ手順と確認用リクエストを用意する。
- 実際のMuseからの接続と実機起動の確認は、利用者の資格情報が必要な検証として区別して報告する。
- 公開前にSQL適用とEdge Function配備が必要。ソースコード追加だけで稼働済みとはしない。

## 費用の前提

2026-11-10確認時点の公式料金では、Freeは月額0米ドル、DB 500MB、
Edge Functions月50万回、外向き転送5GBが含まれる。1週間非アクティブだと停止対象となる。
Proは月額25米ドルからで、追加のプロジェクト・計算資源・超過利用・税等は別途条件がある。
今回の個人検証はFreeで始める提案とし、有料化や外部サービス契約は実装作業から分ける。
Muse自体のプランやメール配信サービスを利用する場合の費用は含まない。

参考: https://supabase.com/pricing

## 実装者に委ねる事項

具体的なファイル分割、UIの小さな配置、SQL/RPCの命名、タイムアウト秒数、
セッション永続化のライブラリ選定、テスト用の依存注入方法は既存コードに合わせて決める。
プロジェクトやアカウントの新規作成、秘密情報の取得、課金、公開環境の変更は実装者の裁量に含めない。
